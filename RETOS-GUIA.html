Guía de retos

Devin Desktop Workshop · Mexico Tech Week · boulder-maze

Un laberinto estilo Pac-Man con una simulación pura y determinista a 60 ticks por segundo (packages/core) y un front-end de Phaser que solo dibuja (apps/web). Tiene reglas serias y buenas pruebas, así que los retos tratan de cambiar las reglas sin romperlas. Hay cuatro retos; no tienes que hacerlos todos.

Cómo trabajar cada reto

Entiende (dale contexto con @-menciones), planea (Plan mode), actúa (Implement) y verifica (tests, Quick Review, Merge).

Antes de empezar

Necesitas Node 22.12 o más nuevo (el repo recomienda Node 24; nvm use lo toma de .nvmrc).

npm install
npx playwright install chromium   # solo si vas a correr los tests e2e (necesita red una vez)

Comandos que vas a usar todo el taller:

  • npm run dev abre el juego en el navegador.
  • npm test corre las pruebas del núcleo (Vitest). Hoy son 55, aunque el README diga 40.
  • npm run typecheck revisa los tipos de todo el repo.
  • npm run validate valida el laberinto. npm run smoke corre 1,200 ticks en Node, sin navegador.
  • npm run test:e2e corre Playwright contra un navegador real.

Controles: flechas o WASD para moverte, P o Esc para pausar. Un solo toque de boulder sin drill y pierdes.

Reglas

  1. Empieza cada reto en Plan mode. Lee el plan, corrígelo y solo entonces aprieta Implement.
  2. En este repo una frase manda: **toda decisión de juego vive en packages/core**. La web solo presenta estado y manda intención de input. Si Devin pone reglas en Phaser, párale.
  3. Las decisiones de diseño son tuyas. Si Devin asume algo que no te gusta, dilo en el plan, no después.
  4. Una sesión por reto. Para el reto Paralelo usa Worktree y revisa con Quick Review antes del Merge.
  5. Que Devin corra npm test, npm run typecheck y te enseñe la salida. Los 55 tests existentes deben seguir verdes, salvo que el plan justifique cambiar alguno.

Ojo con esto

  • npm run typecheck en un checkout recién clonado puede fallar con errores TS2307 sobre @boulder-maze/core. La web consume el núcleo desde dist/: corre primero npm run build.
  • Un Worktree nuevo **no trae node_modules** (está en .gitignore). Corre npm install dentro del Worktree antes de probar nada.
  • Los tests e2e usan el puerto 5199 y reusan un servidor que ya esté ahí. Córrelos de uno en uno; si dos sesiones los corren a la vez, una prueba el código de la otra.
  • La primera corrida de e2e puede fallar por timeout en el arranque en frío de Vite. Repite una vez antes de culpar al cambio.
  • Posiciones y velocidades son enteros (60 unidades por tile). Un valor fraccionario rompe una regla del núcleo sin que nadie se queje al principio.

Retos

Ruta sugerida (~60 min): 1 o 2, y luego 3. Si vas rápido, 4: alcanza con terminar el Nivel 1.

  1. Guardar y cargar (Core, 15–20 min)
  2. Niveles procedurales (Core, 15–25 min)
  3. Sonido y récord (Paralelo, 20–25 min)
  4. Co-op local (Jefe, 25–35 min)

Reto 1 · Guardar y cargar partidas

Core · 15–20 min · Plan mode, Determinismo, Vitest + e2e

El núcleo ya sabe serializarse. Ponle una capa de guardado con validación y úsala desde la web.

La misión

El juego guarda la partida y luego la carga y continúa. El núcleo ya tiene serializeGame y deserializeGame, pero eso no es un sistema de guardado: faltan versión de formato, validación y una capa fina en la web.

La prueba que importa es de determinismo: guardar en el tick N, restaurar y avanzar K ticks debe dar exactamente el mismo estado que la corrida sin interrupción.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Quiero guardar y cargar partidas. Revisa @packages/core/src/sim.ts y @apps/web/src/session/LocalGameSession.ts y propón en Plan mode qué se guarda y cómo se valida al cargar.

Lo que tú decides

  • ¿Qué lleva el guardado? ¿Todo el estado (incluyendo el mapa) o solo lo dinámico? ¿Versión de formato, mapId, mapVersion?
  • ¿En qué fases se puede guardar? ¿Y cargar? Piensa en "ready", pausa, "won" y "lost".
  • ¿Cómo reaccionas a un guardado de otra versión: rechazar con mensaje o migrar?
  • ¿Dónde vive: un slot en localStorage, varios slots, o un archivo JSON? ¿Con qué teclas o botones?
  • Al cargar, ¿la partida se reanuda o queda en pausa?

¿Cómo sabes que terminó?

  • npm test
  • npm run build && npm run typecheck
  • npm run test:e2e

Archivos que vas a ver

packages/core/src/save.ts (nuevo) packages/core/src/index.ts packages/core/test/save.test.ts (nuevo) apps/web/src/session/LocalGameSession.ts apps/web/src/main.ts apps/web/e2e/save.spec.ts (nuevo)

Si te atoras

Pista 1
Piensa en dos capas: una función pura en packages/core que convierte el estado a texto (y de vuelta) con validación, sin tocar el DOM ni localStorage; y una capa fina en apps/web que solo guarda el texto.
Pista 2
Al restaurar en LocalGameSession no basta con asignar el estado: revisa qué otros campos privados de la sesión (acumulador, dirección deseada, eventos pendientes, contador de secuencia de comandos) quedan desfasados. Un contador de secuencia en 0 hace que el núcleo rechace los comandos nuevos.
Pista 3
Envuelve el estado en un sobre con formatVersion, mapId y mapVersion, y haz que loadGame devuelva un resultado ok/error en vez de lanzar.
Trampas conocidas (al final)
  • Después de cargar, el jugador no responde al teclado: inputSeq volvió a 0 y el núcleo rechaza los comandos como duplicate. Debe continuar desde lastCommandSeq del jugador.
  • deserializeGame solo valida cuatro campos. Un guardado manipulado con forma válida pero mapa alterado pasa: compara el mapa contra el esperado o rechaza mapId/mapVersion distintos.
  • F5 recarga la página: necesita preventDefault, y estas teclas no deben pasar por el mapeo de direcciones.
  • El HUD tiene un flag privado ended y un overlayMode: tras cargar, muestra el overlay de pausa para que la UI coincida con la sesión.
  • apps/web consume @boulder-maze/core desde dist/: npm run typecheck falla hasta correr npm run build.
  • Si el puerto 5199 está ocupado por otro servidor, los e2e corren contra código viejo y fallan de forma engañosa.

Reto 2 · Niveles generados proceduralmente

Core · 15–25 min · Plan mode, Algoritmo, Tests de propiedades

Un generador de laberintos que pase el validador. Siempre. Para cualquier semilla.

La misión

Una función generateMaze(seed, opciones) en el núcleo, 100% determinista (nada de Math.random ni Date) que produzca mapas que pasen validateMap para muchas semillas y varios tamaños impares.

El validador es estricto: sin callejones sin salida, sin bloques de 2×2 caminables, al menos 6 cruces, todo conectado, exactamente una P, al menos una o, y cuatro chutes laterales con su metadata. No tiene que ser un laberinto bonito; tiene que ser válido y jugable.

Alcance recomendado: solo el núcleo. Si te sobra tiempo, conéctalo a la web con ?seed=123.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Quiero un generador de laberintos por semilla en el núcleo, que siempre pase validateMap (@packages/core/src/validate.ts). Plan mode primero: dime qué estrategia usarías antes de implementar.

Lo que tú decides

  • ¿Qué estrategia? Retícula de pasillos quitando aristas, simetría espejo u otra. ¿Cómo garantizas cero callejones y conectividad?
  • ¿Cuántas aristas quitas? Más quitadas = pasillos largos y pocos cruces; menos = más cruces y más ciclos. Fija tu propio mínimo de cruces.
  • ¿Dónde van la P, las o y los chutes? ¿Se eligen antes o después de quitar aristas?
  • ¿Qué haces con un tamaño par, o muy chico?

¿Cómo sabes que terminó?

  • npm test

Archivos que vas a ver

packages/core/src/generate.ts (nuevo) packages/core/src/index.ts packages/core/test/generate.test.ts (nuevo) scripts/generate-maze.mjs (nuevo) apps/web/src/session/LocalGameSession.ts y apps/web/src/main.ts (si cableas la web)

Si te atoras

Pista 1
Piensa el mapa como un grafo: los tiles (impar, impar) son nodos, y el tile entre dos nodos vecinos es una arista. Si los tiles (par, par) son siempre pared, ¿qué pasa con la regla de los bloques de 2×2?
Pista 2
Quita aristas en orden barajado con el generador del núcleo, pero solo si los dos extremos tienen grado mayor que 2, el grafo sigue conexo y aún quedan suficientes cruces. Las esquinas nunca quedan como callejón.
Pista 3
Rasteriza a string[]: # por defecto, . en nodos y aristas vivas, y luego sobrescribe esquinas con o, un nodo de la fila de abajo con P y cuatro nodos de las columnas laterales con e.
Trampas conocidas (al final)
  • Si eliges los chutes después de quitar aristas, hay semillas donde ningún candidato conserva su arista hacia adentro y el generador se queda sin chute. Elígelos antes y protege su arista.
  • Un test ingenuo expect(state.tick).toBe(N) falla: la simulación deja de avanzar al llegar a "lost" o "won" (sin input, el jugador pierde en pocos cientos de ticks). Afirma que no lanzó error y que la fase es válida.
  • Los chutes reemplazan el pellet del nodo: no hardcodees el total de pellets, usa el conteo de createGame.
  • Para jugarlo en la web, LocalGameSession tiene el mapa fijo en el constructor y en restart(), y main.ts dimensiona el canvas con ese mapa. Además, MazeScene solo dibuja bien los chutes del lado oeste y este.
  • Después de un npm install limpio, npm run typecheck falla hasta compilar el núcleo (npm run build).

Reto 3 · Dos frentes: efectos de sonido y récord persistente

Paralelo · 20–25 min · Worktree, Paralelo, Quick Review, Merge

Dos agentes, solo en la web, archivos distintos. Que ninguno pise al otro.

La misión

Sesión A: sonidos de juego con WebAudio, disparados por los eventos del núcleo (pellet, drill, boulder destruido, derrota, victoria). Sesión B: un récord de puntaje que persiste entre partidas y se muestra en el HUD.

Cada una en su propia sesión Worktree. Cuando terminen, Quick Review de cada diff y luego Merge. Como las dos viven en apps/web, el reto es respetar las fronteras de archivos.

Dos sesiones, dos zonas

SESIÓN A · SONIDOUn módulo de audio nuevo, enganchado a los eventos que ya recibe la escena. Sin tocar el HUD.
apps/web/src/audio.ts apps/web/src/scene/MazeScene.ts apps/web/src/main.ts
SESIÓN B · RÉCORDGuardado del mejor puntaje y su visualización en el HUD y en el overlay de fin.
apps/web/src/storage/highScore.ts apps/web/src/ui/hud.ts apps/web/index.html apps/web/src/styles.css

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Sesión A (Worktree)

Quiero efectos de sonido con WebAudio disparados por los eventos de @apps/web/src/scene/MazeScene.ts. Plan mode primero. No toques el HUD: otra sesión trabaja ahí.

Sesión B (Worktree)

Quiero un récord de puntaje persistente, mostrado en el HUD (@apps/web/src/ui/hud.ts). Plan mode primero. No toques MazeScene ni main.ts: otra sesión trabaja ahí.

Lo que tú decides

  • A: ¿Cuándo se crea o reanuda el AudioContext? Tiene que ser a partir de un gesto, como el clic en Start.
  • A: ¿Suena algo en pausa? ¿Hay botón o tecla para silenciar?
  • B: ¿Se escribe el récord en cada update() o solo al terminar la partida? ¿Contra qué valor comparas?
  • B: ¿Qué haces si localStorage falla o tiene un valor corrupto?

¿Cómo sabes que terminó?

  • git diff --stat
  • npm test && npm run build && npm run typecheck && npm run test:e2e

Si te atoras

Pista 1
El gancho natural del sonido es MazeScene.onEvent: ahí ya llegan todos los eventos del núcleo.
Pista 2
El HUD marca el fin de partida una sola vez con el flag ended. Ese es el momento de leer y escribir el récord.
Pista 3
Los sonidos son osciladores cortos: una frecuencia, una envolvente y listo. No necesitas archivos.
Trampas conocidas (al final)
  • Un AudioContext creado sin gesto del usuario queda suspendido y no suena. Créalo o reanúdalo en el clic de Start.
  • Si guardas el récord en cada update(), lo reescribes 60 veces por segundo y cuentas mal el "nuevo récord" (compáralo contra el valor anterior).
  • Un Worktree no trae node_modules: sin npm install ahí, nada corre.
  • Los e2e usan el puerto 5199 con servidor reusable: si corren a la vez, una sesión prueba el código de la otra.

Reto 4 · Jefe: modo cooperativo local, dos jugadores en el mismo teclado

Jefe · 25–35 min · Megaplan, Core + web, Reglas de juego

Dos triángulos, un laberinto, cuatro boulders. Sin red: todo corre en el mismo navegador.

La misión

Dos personas comparten el laberinto y los pellets. Cada una tiene su triángulo, su puntaje y su drill. Los boulders tienen que comportarse con sentido cuando hay dos jugadores.

Nivel 1 (obligatorio): reglas en el núcleo y pruebas de Vitest. Nivel 2: web, con P1 en flechas, P2 en WASD, dos colores, dos marcadores y una forma de elegir 1 o 2 jugadores. Terminar el Nivel 1 ya es un buen resultado.

El modo de un jugador debe comportarse exactamente igual que hoy.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Quiero un modo cooperativo local para 2 jugadores en el mismo teclado. Empieza por el núcleo (@packages/core/src/sim.ts). Pide un megaplan y dime las decisiones abiertas antes de implementar.

Lo que tú decides

  • Spawn del 2º jugador: derivarlo del primero (por ejemplo, rotación de 180°) o agregar un tile nuevo al mapa (que obliga a tocar validate.ts, map.ts y mapData.ts).
  • A quién persiguen los boulders: ¿al más cercano? ¿al que va ganando? ¿se reparten? Si hay empate, ¿quién gana?
  • ¿Qué significa "powered" con dos jugadores? ¿Huyen solo del que tiene drill, o de cualquiera?
  • Derrota: ¿compartida (cualquier contacto termina para todos) o por jugador con espectador?
  • Contacto simultáneo: si P1 sin drill y P2 con drill tocan al mismo boulder en el mismo tick, ¿quién muere?
  • Puntaje y victoria: ¿a quién se le acredita la victoria? ¿Qué pasa con el pellet bajo el spawn del 2º jugador?

¿Cómo sabes que terminó?

  • npm test
  • npm run validate
  • npm run smoke
  • npm run build && npm run typecheck
  • npm run test:e2e

Archivos que vas a ver

packages/core/src/sim.ts packages/core/src/map.ts packages/core/test/helpers.ts packages/core/test/coop.test.ts (nuevo) apps/web/src/session/LocalGameSession.ts apps/web/src/input.ts apps/web/src/ui/hud.ts apps/web/src/scene/MazeScene.ts

Si te atoras

Pista 1
Empieza por el núcleo, no por la pantalla. Lo que asume un solo jugador son unos pocos lugares concretos de sim.ts: el spawn, el objetivo de los boulders, el estado "powered" y la victoria.
Pista 2
validateMap exige exactamente una P, así que no agregues otra al mapa: deriva el segundo spawn del primero con una función pura en map.ts.
Pista 3
createGame puede recibir un número de jugadores opcional (por omisión 1). Para los boulders, calcula un campo de distancias por jugador al inicio de cada tick.
Trampas conocidas (al final)
  • El spawn rotado cae sobre un tile que tiene pellet. Si no lo quitas, pelletsRemaining queda inconsistente y el 2º jugador cobra un pellet gratis en el primer tick.
  • El bucle de contactos original itera jugadores por id y se detiene en la primera derrota: con P1 sin drill y P2 con drill sobre el mismo boulder, P1 muere solo por ir primero. Resuélvelo en dos pasadas: primero destruyen los que tienen drill, luego mata el contacto.
  • validateMap rechaza cualquier carácter nuevo en el mapa; agregar una Q de spawn obliga a tocar tres archivos.
  • Los helpers de test asumen un jugador: escribe helpers nuevos en vez de cambiar los viejos y romper 55 tests.
  • npm run typecheck en un checkout limpio falla hasta correr npm run build.
